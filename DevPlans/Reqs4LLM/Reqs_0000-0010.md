- Task 2: 設計一個新的 Text-Based 格式 `StringMap`：佔用記憶體空間最小，整個資料以 RAW DATA (Continuous Memory Space) 的形式固定在記憶體內，任何讀取操作都指向這個 DATA 區段的 Data Position Slice。你也可以用 Swift String UTF8View 來實作這個特性。你自己判斷最優解。總之就是：Memory-Only、Memory-Size-Usage-Minimalized、Lowest-Heap、Fast-Speed。
- Task 3: 為了滿足 Task 2，我允許你對這個專案進行整體 Refactor。你自己判斷 Refactor 之後是否可以刪除對 NCChineseConverter 的 Attribution。
- Task 4: `HotenkaChineseConverter` 既有的方法有沒有徹底的顛覆性的更換方法、讓這個模組的轉換效率更快？

## 調研結果

### Task 1: Deterministic Fixtures

StringMap 的序列化天然 deterministic：排序後的 key/value 行 + 固定 ASCII hex offset table。測試每次重建 `convdict.stringmap`，byte-for-byte 一致。

### Task 2: StringMap 設計

Text-based UTF-8 格式，單一連續 `Data` 常駐記憶體：

1. 檔頭 magic `HTSMAPTXT` + version + dict count + 各字典區段 offset
2. 每個辭典方向有 descriptor：entry count、max key length、index start、data start、data end
3. 固定寬度 ASCII hex offset index table
4. 排序後的 `key<TAB>value<LF>` data block
5. 載入時 CRLF 正規化為 LF
6. 載入後不再建立常駐 trie；轉換時直接查詢 StringMap

### Task 3: Attribution 判斷

已刪除 NCChineseConverter attribution。

在完成 Task 4 的重寫與後續 memory profile 調整後，再進一步刪除 JSON / plist / SQLite / dictDir 全部載入路徑、SQLite3 依賴、以及 String C-level 擴充方法，HotenkaChineseConverter 與 NCChineseConverter 之間已不存在可辨識的 API 或實作血緣：

- 公開 API 不同：`init(stringMapPath:) throws` + `init(stringMap:)` 取代了原本五種非 throwing init
- 轉換核心不同：canonical-normalized direct StringMap lookup + longest-match scan 取代了 repeated substring-query
- 資料格式不同：StringMap 取代了 JSON / plist / SQLite / txt-dir
- 內部結構不同：沒有 `dict` / `dictFiles` / `ptrSQL` / `maximumKeyLengths` / String extensions

保留的只有 `DictType`（六方向列舉，是領域概念而非 NCChineseConverter 特有設計）與 `convert` / `query` 方法名（通用轉換器命名）。

### Task 4: 轉換熱路徑重寫

最終版本不是 trie，而是 canonical-normalized direct StringMap lookup + longest-match scan：

1. 對輸入與 query key 先做 `precomposedStringWithCanonicalMapping`
2. 依字典方向讀取 `maximumKeyLength`
3. 在每個起點從最長候選一路往下縮短
4. 直接呼叫 `StringMap.query(dict:key:)` 做 exact query
5. 命中則輸出替換值，否則原樣輸出一個字元

中間曾實作過 UnicodeScalar trie 版 `PrefixRewriter`，但 memory profile 顯示它會把 StringMap 省下的 retained heap 吃回去，因此已撤回。

# Phase 02

Assignee: Deepseek-v4-flash.

> 與先前一樣：施術之後請恪守 `DevPlans` 目錄下的 KnowledgeMemo 裡面的 Response Pattern 完成 markdown 文件的記錄工作。本 Phase 為 vChewing-macOS Phase 152 第三波的鏡照（事主指定：對 Hotenka 原廠語料的修改內容需鏡照至本倉庫）。

## 需求背景與任務

vChewing 康熙模式（zh2KX 轉換）的「一對多」語義誤轉清查後，發現單字對映 `才→纔`、`參→蔘`、`核→覈` 會把常見義項（才華／參與／核心）誤轉成罕見義項的古典字形（天才→天纔、參加→蔘加、核心→覈心）。字詞層的根治需修改本倉庫的 zh2KX 字典語料。

任務：

1. 移除 zh2KX 三條破壞性單字對映（才→纔／參→蔘／核→覈），讓常見義項預設正確。
2. 補上罕見義項的詞條消歧（剛才→剛纔、人參→人蔘、核實→覈實等）。
3. 重生 `convdict.stringmap`，確保與 vChewing 各倉（macOS／OSX-Legacy）生產檔逐字節一致。

## 設計決策

勘查語料量級後（VanguardLexicon 詞庫含「才」的詞多達數百條、罕見成語居多）採**移除式**設計，而非逐一列舉常見義項詞條：

- 移除式：移除破壞性單字對映後，含這些字的所有詞（含未列舉的罕見成語）預設皆正確。
- 漏網的罕見義項詞維持原字（才／參／核皆為合法字，且「才」作方才義本屬古典用法）——錯誤由「語義誤傷」降級為「未轉古典字形」，良性。
